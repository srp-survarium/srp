v0.21d lifecycle implementation and three-client test
2026-10-11; feature/server-v021d

IMPLEMENTED, WITH LIVE FINISH VALIDATION STILL PENDING

The fixed-cohort server now ends a timed match by sending each client server
0x57 for its OWN slot when the deadline is reached. It uses the same duration
as static setup and includes the ten-second countdown. For the current fixed
setup, wait_player_percent=0 and every player activates together. Deadline is
activation + countdown_seconds*1000 + match_seconds*1000. This is not a general
replacement for engine victory rules or arbitrary waiting/countdown options.

The message is sent at the deadline, not earlier with a future timestamp:
the local-slot handler closes immediately. Normal remote-player leave events
retain the existing future simulation-time scheduling. Once finishing, reject
new inputs, retain peers/transport until disconnect or timeout so reliable
finish delivery can retry, and suppress redundant leave broadcasts. The last
peer's removal clears lifecycle state and permits a new starting cohort.

CLI now accepts an optional fourth argument:
  match-server-021d SESSIONS_FILE [PORT] [START_PLAYERS] [MATCH_SECONDS]
Duration defaults to 600 seconds and must be a nonzero u16. A short duration
is intended to make lifecycle tests repeatable; countdown remains 10 seconds.
This does not populate results, determine an early battery victory, persist
scores/rewards, or provide the lobby's missing profile/statistics responses.

POPULATED STATE BOUNDARIES

New state.rs validates the serialized player mask against static roster size,
each sized player block, the variable compressed-animation boundary, and four
sized world blocks, rejecting truncation and trailing data. Any nonzero
animation flag is true, matching the engine. It preserves every original byte.
The animation bitstream is MSB first; its tree/time/float dictionary boundaries
follow decode_data 0x25dc1d, decode_times_in_ms_impl 0x25d9ba and
 decode_floats_impl 0x25db10 (see HDD PROTOCOL.txt).

The original capture passes: 59,743 datagrams verified, all 17 world layouts
(11 uploads and six downloads) consume exactly their complete bodies. All six
uploads with a captured same-time CRC still match. Unit tests exercise direct
and dictionary animation modes, all truncated prefixes, mask bounds, flag
semantics and invalid sizes. This is boundary validation, not validation of
physics, animation-tree contents or inventory semantics. Populated snapshot
selection, membership/CRC eligibility and recovery replay remain to implement.

Thirty tests pass: 27 unit and three executable/UDP integration tests. The new
socket test starts two clients with a one-second match plus ten-second
countdown, drops one finish packet and verifies the retry reaches both local
slots with the correct deadline. This is not proof of the engine's UI result.

RESOURCE CHECK (NOT A CAPACITY BENCHMARK)

During the live three-client match, debug server PID 3207723 had RSS/high-water
2,884 KiB, one thread, four FDs, TracerPid zero, and consumed 0.8% of one CPU
core over a five-second wall-clock sample. The first 95.66 seconds of captured
match traffic averaged 2,027 outgoing and 1,828 incoming IPv4 bytes/second.
This small match had limited input activity; it cannot directly predict ten
full 20-player matches. Server does no rendering or engine simulation.

Current executable owns one match/socket. Separate processes/UDP ports could
host multiple matches, but the front door still routes every test account into
one fixed cohort. Match assignment, session routing and process lifecycle need
implementation for ten managed concurrent matches. Relay fan-out grows roughly
as N*(N-1) within each match. A realistic concurrency/loss benchmark remains
necessary; these observations are not a hardware sizing guarantee.
