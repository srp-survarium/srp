NEW INTEGRATION FINDING: NATIVE MATCH CHAT

The accepted chat test in CHAT-RECONNECT.txt used the community fixed-roster
front door. It must not be silently generalized to the newly included native
multi-match service. native_menu.py installs front.Messaging unchanged, while
its redirect callback updates neither LocalState.redirected_slots nor the
single-match front-door route. Messaging.relay currently requires group==1
and membership in redirected_slots for channels 5/6/7. Consequently a fresh
native menu store cannot relay match/team chat through that path.

Simply setting redirected_slots would be insufficient: team assignment in a
native room follows its match-roster index, not the persistent account slot,
and concurrent rooms must not receive each other's match/team messages even
if a client subscribes to another room's group. Fix this using allocator-owned
membership and team identity. First trace the actual client group source:
native admission orders advance, whereas static setup still uses match ID1.
Add automated multi-room tests; the user's accepted community chat/gameplay
test does not need repeating.

CLOCK EVIDENCE FOUND DURING THIS AUDIT

try_send_all 0x1a310b floors the supplied simulation timestamp to a 50ms
boundary for its send schedule. At 0x1a32be it checks last-send+1000ms, then
requires a populated state history/event-horizon item. The emitted client44
body comes from floating_timer::get_elapsed_msec (0x1a3309), not that rounded
simulation timestamp. Lost/unordered 44 notifications have no reference ID.

Dispatcher 0x1a160f..0x1a1626 reads the two-byte server55 offset and calls
floating_timer::set_offset (0x150d70). The latter first rebases the running
timer, chooses a signed floating factor and sets its duration from the offset.
The referenced float constants are -1 at0x836f08, +1 at0x876f40 and1000 at
0x836efc. Positive offsets speed up, negative offsets slow down; a new offset
replaces the previous correction's remaining interval. The configured factor
magnitude at timer+0x28 still needs tracing before choosing a cooldown.
These are client facts, not a recovered policy of the community server.
