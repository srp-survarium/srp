CHAT CONTROLS

Both test user.cfg files bind chat=kT, send_message=kRETURN, send_to=kTAB.
With chat focused, Tab selects the next channel and Shift+Tab the previous
channel. Select the match channel to reach both teams, then Enter to send.
The client remembers the selected tab; our first automated message used Team
and therefore correctly did not reach the opposing player.

Binary chat_handler::on_keyboard_action at0x1631f2 uses action0x45 for this
switch and calls root.next_tab or root.previous_tab depending on Left Shift.
Action0x44 sends/finishes typing. Key bindings, not an assumption from another
game/build, establish the actual keys in these test prefixes.

WIRE CONTRACT AND IMPLEMENTATION

The messaging connection is framed TCP on12024, separate from match UDP12023.
Existing c3 sign-in is u32 session plus client type5 (account). The server
resolves the session to a fixed-roster slot and replies ca + u8-string name.

on_message_typed at0x19b0ff writes:
  c1,u32 channel-group,u8-string recipient,u8 channel,u8-string message.
process_incoming_text_message at0x19b858 reads:
  c9,u8 sender type,u32 sender ID,u8-string name,u8 channel,u8-string message.
update_channel_subscriptions at0x1b3441 writes:
  c5,nine LE u32 group IDs indexed by channel.
Strings are byte-length-prefixed; text bytes are forwarded without recoding.

Supported routes: general1 by matching subscription group, private4 to a
case-insensitive Local N name, match5 for this test's match-order1, and team6/7
for alternating fixed-roster teams. Match/team sending requires the slot to
have received the match redirect. Team identity is derived from the signed-in
slot; a client cannot choose the opponent's team by changing its channel byte.
Recipients must have the matching channel subscription. No sender echo:
on_message_typed already adds the local display message before transmitting.
Server names/IDs come from the authenticated slot, not client-supplied text.

Messages validate string boundaries, exact payload length, recipient length
and embedded NULs. Existing TCP framing supports partial stream reads and
long frames. Per-recipient write locks prevent interleaved outgoing frames.
No account/password/chat text is printed by the relay; logs contain slot,
channel, payload length and recipient count. Clan/squad/friends/history are
not implemented. This is still the local fixed-roster companion, with blocking
socket writes, not a production messaging service with slow-reader isolation.

Messaging reconnect replaces any old socket for the same slot, shuts down the
old connection and guards cleanup by connection identity so it cannot remove
the new registration. This is separate from redirecting a client back into an
ongoing UDP match, which remains the failed boundary described above.
